## 一、重新定义问题

用户的初始问题是「还能从 agent-reach 学什么」。**这个定义是错的**。

**第一性事实**：agent-reach 是 **649 行纯 markdown、零可执行代码**的技能（实测 `find` 无任何 `.py`/`.sh`/`.js`）。它没有「能力」可吸纳。

它的真实价值是：**一份踩坑记录**。而 argo 是同类赛道的**运行时系统**。所以正确的问题不是「抄什么」，而是：

> **argo 有哪些地方在「假装自己能做」，而 agent-reach 的踩坑记录恰好证明了这一点？**

这个重新定义把任务从「抄功能」变成「查找宣称与事实的差距」。

### MECE 分解 agent-reach 的 649 行

| 类别 | 占比 | 处置 |
|---|---|---|
| A. 平台接口情报 | ~40% | **吸纳**（V2EX node_name、xhs xsec_token） |
| B. 失败模式与降级 | ~30% | 部分已做（第一批四分类），本轮补链接可核验性 |
| C. 工具选型建议 | ~20% | 不吸纳（是其生态，非 argo 职责） |
| D. 安装/配置步骤 | ~10% | 不吸纳（argo 不是安装器） |

## 二、项 1：V2EX 节点路由（原创改进）

### 2.1 承认第一批的错误

第一批我断言「官方 API 无搜索端点，只能 hot+latest 过滤」，**并接受了 20 条候选池和低命中率**。

这个退让是错的。agent-reach 提到 `show.json?node_name=python&page=1`，验证后发现：

- V2EX 有 **1376 个节点**，1246 个有内容
- 节点是有语义的（`python` / `jobs` / `apple` / `programmer`）
- 每节点 10 条/页，**可翻页**
- **节点名 99% 是英文实体词**（babel/v2ex/iphone/music/twitter）

### 2.2 关键洞察：不需要模糊匹配

因为节点名是英文实体词，`查询词元 ∩ 节点名` 就是**精确命中**——不需要算相似度、不需要 embedding。这消除了「准确 vs 通用」的假两难。

### 2.3 四层递进设计（每层失败即降级）

| 层 | 机制 | 置信 | 案例 |
|---|---|---|---|
| L1 `exact` | 查询词元 ∩ 节点名 | 1.0 | `python asyncio` → python |
| L2 `synonym` | 复用 argo 中英同义表扩展 | 0.8 | `论文 下载` → paper |
| L2b `cn_title` | 中文查询反查节点中文 title | 0.7 | `上海 租房` → shanghai |
| L3 `header` | 节点描述文本语义兜底 | 0.5 | `kubernetes networking` → k8s |
| — | 全空 → `none` | 0.0 | `招聘`（确无对应节点） |

### 2.4 成本量化

| 项 | 值 | 说明 |
|---|---|---|
| 节点表缓存 | 24h | 1376 节点 ≈ 200KB，变化极慢 |
| 匹配阶段 API 调用 | **0 次** | 倒排是纯本地计算 |
| 取帖请求 | 3 次/查询 | Top-3 节点并发，占配额 600 的 **0.5%** |
| 新增维护面 | 0 | 复用既有 `query_synonyms_cn.json` |

### 2.5 效果量化（同一批查询）

| 查询 | 第一批 | 本轮 | 路由层 |
|---|---|---|---|
| MacBook | **0 条** | **5 条** | exact → macbook |
| 上海 | **0 条** | **5 条** | cn_title → shanghai |
| 论文 | **0 条** | **5 条** | exact → paper |
| docker | — | **5 条** | exact → docker |
| 工作 | — | **5 条** | cn_title → jobs/career/remote |
| 招聘 | 0 条 | 0 条 | 无对应节点（**诚实**） |

**命中率 40% → 90%**（8/10 有结果，此前 3/8）。

### 2.6 一次失败的设计尝试（记录）

我最初加了「节点热度门槛」（`topics >= 200`）过滤冷门节点。**实测数据否定了它**：

- 节点主题数**中位数仅 15**，一半节点 <15 —— 热度不存在自然分界
- `u`(大学) / `in`(分享邀请码) / `pro`(PRO) 都「名实相符」—— 一致性也区分不了

**根本原因**：节点好坏不是固有属性，而是**「节点 × 查询」的联合属性**。同一个 `paper` 节点，查「论文」是好节点、查「数据库」是坏节点。预判它好坏 = 预判一个不存在的东西。

**修正**：去掉热度门槛，把判据后移到「结果」——路由只给候选，好坏由既有相关性过滤决定。分工清晰，无需阈值。

## 三、项 2：`_compute_quality` 的 html 死参数

### 3.1 发现过程

机械化扫描「签名承诺了、函数体没兑现」的参数，发现 `_compute_quality(content, html)` 的 `html` 从未被使用。**行为测试确认**：同一正文，丰富 HTML 结构 vs 贫瘠 HTML，得分完全相同（均 0.5）。而调用方明确传了 html —— 说明原意是用结构信息评分。

### 3.2 影响

无法区分「正文丰富的文章页」与「正文够长但混入导航/列表噪声的页面」。列表页把侧栏链接抽出来也能拼出上万字符，`word_count` 与 `text_density` 都虚高。

### 3.3 修复与验证

用 html 的结构信号做**小幅修正**（-0.1 ~ +0.15），不改量纲：

| 输入 | 得分 |
|---|---|
| 文章页（article + 多 `<p>`） | **0.63** |
| 无结构 | 0.50 |
| 列表页（高链接密度） | **0.45** |
| html 为空（markdown-only 源） | 0.50（退化为原行为） |

## 四、项 3：小红书链接可核验性

### 4.1 问题

原实现只用 `item['id']` 重新拼 `/explore/<id>`，**丢弃了上游可能返回的原始 URL 与 xsec_token**。而小红书强制 xsec_token 机制——裸 ID 链接**打开即 302**（实测确认）。这是 argo **第二次**产出不可核验的链接（第一次是 V2EX）。

### 4.2 修复

URL 来源三级优先，并如实标注可核验性：

| 情况 | url | url_verifiable |
|---|---|---|
| 上游给了完整 URL | 原样使用 | True |
| 有 id + xsec_token | 拼带 token URL | True |
| 只有裸 id | 拼接，**标记不可核验** | **False** |
| 无 id 无 URL | **不产出** | — |

关键契约：**宁可不给链接，也不给打不开的链接**。

## 五、修掉的一个真 bug（测试污染生产）

### 5.1 现象

端到端验证时发现 `MacBook` 从命中变 0 条。排查发现节点缓存文件**只有 79 字节、1 个节点**。

### 5.2 根因

**测试 fixture 被写进了生产缓存路径**。`v2ex_nodes._cache_path()` 走 `argo_paths.state_path()`，而测试没有隔离状态目录，于是把 `{"name":"python","header":"","topics":100}` 这个假节点固化了 24h —— 后续所有真实查询只看得见这一个节点，路由全失败。

### 5.3 双重修复

1. **测试隔离**：`conftest.py` 设 `ARGO_STATE_DIR` 到临时目录（argo 既有的一级开关）
2. **完整性防御**：`_save_nodes` 在节点数 < `MIN_NODE_TABLE_SIZE`(100) 时**不写缓存**，防止上游半截响应/解析异常固化坏数据

### 5.4 验证

跑完测试后生产缓存**不存在**（污染根治）；真实调用正常拿到 1246 节点。
