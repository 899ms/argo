## 二、项 1：缓存软命中跨引擎污染

### 2.1 根因（与初始判断不同）

初始判断是「缓存未隔离 engine 维度」。**实测根因不同**：缓存键 `_key()` 里 engine 是参与哈希的
（`f"{kind}|{nq}|{engine}|{domain}|{mode}|{depth}"`），主键隔离本来就是对的。

真凶在**语义软命中分支**：

```python
# scripts/cache.py:734（修复前）
similar = self._l2.find_similar(query, engine, domain)   # ← engine 传了
```

而 `find_similar` 的 SQL **WHERE 子句不含 engine**，只过滤 domain：

```sql
SELECT key, query, domain, ttl, created_at
FROM search_cache WHERE domain = ? ORDER BY accessed_at DESC LIMIT ?
```

形参收了，函数体里一次没用——与账本记过的 `stop_signal` 死分支同类。

### 2.2 实证

三次不同 engine（`v2ex` / `xiaohongshu` / 不存在的引擎名）调用 `find_similar`，
**返回结果字节级一致**。扫描真实缓存库（`~/.cache/unified-search/cache.db`，1068 条）
发现 6 组跨引擎近重复对，其中高危组合：

| 相似度 | 缓存项 A | 缓存项 B |
|---|---|---|
| 0.875 | `.../image-prompting` | `.../image-prompting.md` |
| 0.75 | `promptessor.com/blog/gpt-image-2-5-...` | `morphic.com/resources/models/gpt-image-2-5` |

第二行是**两个不同站点 URL 被判为「近重复查询」**（阈值 0.7），说明 fetch/evidence
的 URL 缓存会互相串正文。

### 2.3 修复

`scripts/cache.py`：
- `find_similar` 的 SQL 增加 `AND engine = ?`；`engine="auto"` 保留为显式通配
- 组合键（`a+b`）不参与软命中：组合结果集是融合产物，与单引擎缓存不可互换
- L1 回填改为存「本请求视角」载荷（含 `_semantic_hit`/`_semantic_query` 标记），
  不再存他人原始 `s_hit`

### 2.4 一处判断修正（重要）

初版报告称「L1 回填他人 `s_hit` 致污染跨过期周期存活」。**此判断错误，已纠正**：
`s_hit` 来自 `_l2.get()`，是 L2 存库时已带 `_ttl`/`_ts` 的完整载荷，
L1 过期判断正常工作。用 git 原版复现确认 `_ttl=3600` 存在。

真实问题是**软命中标记丢失**：L1 二次命中返回 `_semantic_hit=None`，
调用方无法区分「精确命中」与「相似但不同的查询命中」。对照实证：

```
修复前：第1次 L2/_semantic_hit=True/sim=0.75 → 第2次 L1/_semantic_hit=None/sim=None
修复后：第1次 L2/_semantic_hit=True/sim=0.75 → 第2次 L1/_semantic_hit=True/sim=0.75
```

## 三、项 2：V2EX 引擎产出幻觉

### 3.1 根因（比初始描述更严重）

初始判断是「URL 写成搜索页」。**真实根因是抓错了页面**：

```
GET https://www.v2ex.com/search?q=python
  → 302 Location: /go/search
```

`/go/search` 是「**搜索引擎技术研究**」**节点页**，不是搜索结果页（站内搜索需登录态）。
旧实现用 `item_title` 正则直接抓该页面，于是把节点热帖当成了搜索结果。

产出特征：三条信息没一条来自真实帖子——
- `title`：如「装机 配置 预算」，与查询无关（节点热帖）
- `url`：恒等于查询自身的搜索页地址
- `snippet`：硬编码常量「V2EX 社区讨论」

更麻烦的是**上游全绿**：`coverage.status="ok"`、`returned=10`、`latency_ms=3549`。
熔断器/健康度/准入都认为它健康——失败伪装成成功。

### 3.2 关键情报

V2EX 官方开放 API **没有搜索端点**（探测 `/api/search.json`、`/api/topics/search.json`
均返回 HTML 而非 JSON）。可用接口：

| 接口 | 说明 |
|---|---|
| `/api/topics/hot.json` | 热门主题（10 条） |
| `/api/topics/latest.json` | 最新主题 |
| `/api/topics/show.json?id=` | 主题详情 |
| `/api/replies/show.json?topic_id=` | 回复列表 |

带 `rate_limit: {used, quota: 600}` 配额字段。

### 3.3 修复方案

因 API 无搜索，策略改为「**拉候选池（hot+latest 去重）→ 本地相关性过滤排序**」：

- 产出的每条结果带真实 `/t/<id>` 链接、真标题、真正文、真回复数
- **候选池内无相关主题时诚实返回空**，不回落伪造占位结果
- `social_meta` 标注 `retrieval_mode: candidate_pool_filter` 与 `pool_size`，口径透明

### 3.4 迭代中修掉的两个自己引入的缺陷

**① 节点名参与匹配太宽**：查询「V2EX 社区」命中了「推广」节点简介。
修复：只匹配标题与正文，不匹配节点名/简介。

**② 短词子串误命中**（攻击测试发现）：
- 查询 `a` → 命中 Apple/astar，返回「如何充值 chatgpt」「东京夜生活」
- 查询 `ab` → 命中 Avalonia/Wabou/Workbuddy

修复过程中先试「门槛提到 3」，但发现会**误伤 `ai`**（有真实语义的双字符词，
实测返回 0 条）。最终正解是**词边界感知**：

```python
if CJK(term):      return term in blob                    # CJK 无词边界概念
if len(term) < 2:  return False                           # 单字符拉丁词放弃
return re.search(rf"(?<![a-z0-9]){term}(?![a-z0-9])", blob)  # 拉丁词边界
```

验证结果（10/10 符合预期）：

| 查询 | 结果 | 说明 |
|---|---|---|
| `a` / `x` | 0 条 | 单字符门槛 |
| `ab` | 0 条 | 词边界挡住 Avalonia/Wabou |
| `ai` / `AI` | 1 条 | 双字符有语义词保留 |
| `Avalonia` | 1 条 | 精确词 |
| `编程助手` | 1 条 | CJK 子串 |

### 3.5 存在的局限（诚实披露）

候选池只有 10+10 条，**长尾/冷门查询命中率偏低**。实测：

| 查询 | 结果 |
|---|---|
| iPhone | 5 条 |
| Claude | 5 条 |
| 程序员 | 1 条 |
| MacBook / 招聘 | 0 条 |

这是**官方 API 无搜索接口的固有代价**，不是实现缺陷。已在 `social_meta.retrieval_mode`
中标注口径，让调用方知道「0 条 = 池内无相关主题」，而非「V2EX 上没有」。

## 四、项 3：依赖声明 + 失败归因

### 4.1 `requires` 依赖声明（B1）

**问题**：`config._validate_engine_paths` 只检查 `cmd[-1]` 指向的脚本文件是否存在。
对「壳脚本」型引擎完全无效——`python3 scripts/social_engines/xiaohongshu_engine.py`
的脚本当然存在，状态显示 `ready`；但脚本内部真正调用的 `xhs` 二进制缺失，
调用后白等到超时、返回 0 条，无从知道缺什么。

新增 `scripts/engine_requires.py`，声明式后端依赖（与既有 `required_env` 同构）：

```yaml
requires:
  - bin: xhs
    fix: npm i -g xiaohongshu-cli
    optional: false
  - bin: rdt
    optional: true    # 有降级链时缺失只降级，不算故障
```

状态机 `scripts/engine_status.py` 增设 `missing_dep`，并加入 `routable` 条件。

**落地实证**（`--list-engines --detail`）：

| 引擎 | 修复前 | 修复后 | 说明 |
|---|---|---|---|
| `xiaohongshu` | ready / routable | **missing_dep** / 不可路由 | 缺 `xhs`，带安装命令 |
| `twitter` | ready / routable | **missing_dep** / 不可路由 | 缺 `tw`，带安装命令 |
| `reddit` | ready | ready | `rdt` 为 optional，有 JSON API 降级链 |

### 4.2 失败四分类（B3）

熔断器只回答「要不要继续用」（open/closed/disabled），不回答「为什么坏」。
新增 `scripts/engine_failure.py`，把失败归类并给动作：

| 分类 | 触发信号 | 动作 |
|---|---|---|
| `dependency` | 声明的依赖缺失、FileNotFoundError、command not found | 按 requires.fix 安装 |
| `auth` | 401/403、login required、cookie expired、登录已过期 | 重新登录、进登录态分区 |
| `upstream` | 404/410/5xx、parse error、接口已变更 | 更新引擎解析实现 |
| `network` | 超时、连接重置、DNS、SSL | 重试/换网络，通常无需改代码 |

判定优先级：**声明事实 > 异常类型 > HTTP 状态码 > 文本模式（auth→dep→upstream→network）
> unknown**。信息不足时返回 `unknown` 而非硬猜——错的归因比没有归因更坏。

13 个分类用例（含中文信号）全部归类正确，已接入 `runtime.failure` 字段。

### 4.3 附带修复：编码门禁

新增 `engine_requires.py` 的 `subprocess.run(..., text=True)` 被
`tests/test_hardening_0902.py` 的跨平台门禁拦下（Windows GBK 会乱码/崩）。
已补 `encoding="utf-8", errors="replace"`。**这个契约测试有效，值得保留。**
