# 对标研究：OmniGet 获取层机制 → argo 吸纳清单

日期：2026-09-12
源码：`GPT/tmp/omniget-study/`（浅克隆 github.com/tonhowtf/omniget，GPL-3.0）
定位：本研究只取「对不可控第三方站点做可靠数据获取」的工程机制；功能清单层面 omniget 与 argo 领域不同。

## 仓库定性

OmniGet 是一个下载器/媒体工具箱（Tauri 2 + Rust + SvelteKit，yt-dlp GUI 壳 + 108 工具 + 插件系统 + 本地 MCP 桥），10.2k stars。它面对的核心问题与 argo 高度同源：向大量不受自己控制的站点发起请求，在封锁、限流、登录墙、环境差异下保持成功率，并且让失败可解释。

它的价值在获取层的六套机制，不在工具数量。以下按对 argo 的价值排序。每条附 omniget 源码位置与 argo 现状核实结果。

## 吸纳清单

### P1 错误诊断层：每个命名原因配唯一 remedy

omniget：`src-tauri/src/core/root_cause.rs`。把 stderr 翻译成 7 个命名原因（rate_limited / needs_login / tls_fingerprint / extractor_outdated / disk_full / po_token_required / sabr_only），每个原因绑一个 remedy 动作（WaitAndRetry / ImportCookies / UseImpersonation / UpdateYtdlp…）。三条纪律值得整段抄：

- 顺序敏感，具体特征优先。`members-only + 403` 归 needs_login，纯 `403` 归 tls_fingerprint——「乱建议比不建议更糟」。
- 不知道就返回 None，拒绝发明原因。
- 原因清单与 i18n key 清单用测试互相锁定，加新原因必须同时补 key。

argo 现状：HttpClient 已尊重 429/503 Retry-After + 指数退避（`scripts/engines_base.py:269`）；`_detect_anti_bot` 已有拦截特征词表（`scripts/engines_base.py:505` 附近）。但这些最终都归约为同一个「失败」信号；429（等一会儿就好）、指纹封锁（换客户端形态可解）、DNS（本机网络问题）、内容为空（引擎真该降权）四者结局应当不同，现在可能走同一条失败→降权路径。

建议：新增 `scripts/root_cause.py`，`diagnose(error_text) -> {cause, remedy}`，remedy 枚举直接对齐 argo 已有动作：

| cause | remedy | argo 侧动作 |
|---|---|---|
| rate_limited（429/Retry-After） | wait_retry | 退避重试，**不降权** |
| fingerprint_block（_detect_anti_bot 命中） | switch_client_form | 标记封锁，路由换引擎，doctor 单列 |
| needs_auth | rotate_credential | 配额探针/凭证轮换提示 |
| network_error（DNS/超时） | report_network | 不降权单引擎，归环境 |
| empty_or_junk（内容空/质量差） | deprioritize | 现行降权路径 |

现有防饿死与 learner 重排逻辑接在这个诊断层之下，判据从「失败次数」变成「失败原因」。

### P2 并发桶 + 最小间隔写进 engine_registry

omniget：`src-tauri/src/core/host_limiter.rs`。两个机制：① 域族归一——x.com / twitter.com / twimg.com 归同一个 `twitter` 桶（CDN 域与主站共享预算，11 个站点的归一表）；② 每桶双层节流——并发信号量（默认 4，敏感站 2~3）+ 相邻请求最小间隔（YouTube 1500ms、Instagram 2000ms）。

argo 现状：已核实 `backends/engine_registry.yaml` 无任何 concurrency / interval / throttle 字段；配额只有次数/天粒度（quota_profiles.json，zhihu 5000/天等）。fan-out 并行时对同一引擎的多次调用没有突发约束。

建议：engine_registry 引擎条目加 `max_concurrency`、`min_interval_ms` 两字段，HttpClient 统一出口执行；把域族归一表也抄过来（知乎主站与 API 域、X 与 twimg 这类同族域共享桶）。成本极低，直接减少 429。

### P3 封锁与死亡分开记账：「被挡住的引擎没坏」

omniget：`omniget-core/src/core/impersonation.rs`。启动时解析 `yt-dlp --list-impersonate-targets` 先知道能力（「先知道再试」）；封锁特征独立成词典（handshake failure / just a moment / cloudflare / enable javascript / 403）；修复方案是换 TLS 指纹（`--impersonate Chrome-133:Macos-15`，curl_cffi 提供），优先桌面 Chrome。

argo 现状：`_detect_anti_bot` 命中后与普通失败同桶。duckduckgo 本机 45% 错、Nominatim 不通这类「环境级事实」目前靠 live eval 人工归因。指纹封锁的引擎被降权属于冤案。

建议：`_detect_anti_bot` 命中改标 `cause=fingerprint_block`；live eval 与 doctor 报告把引擎状态分三列——被封（有救：curl_cffi 客户端或 kimi-webbridge 浏览器态路由）/ 真死（下线或降权）/ 限流（等待）。argo 已有的「浏览器态走 kimi-webbridge」路线正好是被封引擎的升级通道。

### P4 同一资源多路由级联，按认证成本排序

omniget：`omniget-core/src/platforms/twitter.rs`（1013 行）。一条推文五级通道：GraphQL（带浏览器 cookie）→ Guest Token → Syndication API（免登录，token 由 tweet_id 的 base36 变换直接算出，`calculate_syndication_token`）→ HTML 页面抽取 → yt-dlp 兜底。每级失败落到下一级，认证成本从高到低。

argo 现状：twitter 是单通道 cli 引擎，另有 fxtwitter spec（spec/ 层垂直源）。X 直接抓 403 是已知痛点。

建议：引擎规格支持 `fallback_chain` 声明；twitter 补 syndication 通道（免登录、token 算法公开，omniget 源码可直接参考算法描述）。X 类资产的到达率会直接受益。

### P5 批量任务预检报告

omniget：`src-tauri/src/core/preflight.rs`。批量执行前先跑一轮探测，把每个条目分成 Unsupported / NeedsAuth / NotFound / AlreadyHave 四类问题；`is_actionable` 区分「用户能解决」（需要登录）与「平台不能解决」（站点不覆盖）；verdict 三档 Go / GoWithSkips / Stop。两条细则：磁盘读不出来（None）不阻塞——别把可能的问题换成确定的问题；无大小估计的条目不算 0，跳过求和继续。

argo 现状：批量抓取（article / job / 归档回填）直接全量跑，跑到一半才知道一半要失败。

建议：批任务加预检轮，输出预检报告再全量执行。AlreadyHave 与 wayback_cdx / archive_org 联动——已有快照的 URL 跳过原文抓取；NeedsAuth 域名提前列出。这与「没实施的不介绍」一致：先在 article 一条命令上试点。

### P6 脱敏发生在记录时

omniget：`src-tauri/src/core/flight_recorder.rs`。全局环形缓冲最近 500 条事件用于 bug 报告；关键设计是 `record()` 入口先 redact 再入缓冲（「导出时再脱敏，依赖没人忘记调用出口函数」）；redact 按秘密类别实现并逐类测试：`cookie=` / `token=` / `access_token=` / `SESSDATA=` / `bili_jct=` / `Bearer` / home 路径改 `~`。

argo 现状：run 归档为 jsonl（`data/argo-search-archive/`）。多数引擎 key 走 query 参数或 header，归档若原样记 URL，则归档文件本身含密钥；对外分享归档/日志时有泄漏面。

建议：归档与 debug 输出的写入路径加同款 redact（类别正则 + 每类一条测试）。与工作区隐私规则（密钥不入库、输出脱敏）同源，属于补齐而非新方向。

## 明确不吸纳（做减法）

- 下载器本体（yt-dlp / aria2 / BT / 断点队列）、108 工具箱、播放器 / Anki / 阅读器：领域不同。
- 本地 MCP 桥（31 工具）：与「MCP 按需化、无状态单发走 CLI」既定原则相反，argo 走 CLI 是对的。
- whisper.cpp 转写：不进 argo。但它印证了 dbs-video-extract 待拍板方向（短视频语音转写空白）的真实需求；TikHub / 轻抖拍板时本地转写可作为对照路线。
- 按频道/主机自动归档的规则系统：argo 的 ROUTE_MATRIX + domain_profiles 已覆盖同类需求。

## 一个总体观察

omniget 的模块注释都在回答「这个机制为什么存在、原来的错误前提怎么被修正、取舍是什么」。反复出现的三句纪律——先知道再试、乱建议比不建议糟、测量失败不阻塞——与 argo 的 fail-open、词面覆盖守卫是同一种哲学。P1~P6 落地时，建议把这三句作为 argo 侧对应模块的验收口径：诊断层不许猜原因、预检报告不许阻塞在测不出的项上、引擎健康先探针后结论。

## 落地顺序建议

1. P2（registry 两字段 + 域族归一）——半天量级，纯减法收益。
2. P1 + P3（root_cause 诊断层，_detect_anti_bot 结果并入）——live eval 口径同步改三列。
3. P4（twitter fallback_chain + syndication 通道）——按 ADDING_NEW_ENGINE 流程走。
4. P5、P6——分别挂在 article 批量与归档写入路径上试点。

每步跑全量测试 + offline 门禁 + live 抽查，按既有回归纪律执行。
