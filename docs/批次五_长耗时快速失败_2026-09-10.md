## 一、结论速览

**你的判断是对的。** 31 秒不是网络慢，是**重试叠乘**造成的设计缺陷。

| 项 | 修复前 | 修复后 |
|---|---|---|
| 单引擎最坏耗时 | **31.3s** | **10.1s**（预算上限）|
| 中文查询 | 1.10s | **0.80s** |
| 英文查询 | 4.29s | **1.33s** |
| 日文查询 | 8.40s | **3.06s** |
| anysearch 单引擎 | 31.3s | 2.4~6.6s |

顺带发现并修掉**批次三自身的一个潜伏 bug**（中日语言误判为兼容），
见 §5。

## 二、根因：重试叠乘（不是网络慢）

### 2.1 拆解 31 秒

```
引擎级重试  retry_count = 1        → 2 次尝试
HTTP 级重试  max_retries = 1       → 2 次尝试
单次超时     timeout = 8s
                                   最坏 2 × 2 × 8 = 32s（实测 31.3s）
```

**为什么引擎级重试会被施加**：`search._engine_retries()` 有一条设计好的
逃生门——「已声明 `spec.timeout ≥ 8s` 的引擎不再叠加引擎级重试」。
而 `anysearch` **在 config 里没声明 timeout** → 返回 `retry_count=1`。

**为什么 HTTP 级重试存在**：`anysearch` 的 builder 里写死 `max_retries=1`。
（对比：通用 HTTP 引擎走 `_http_get_raw` 时显式用 `max_retries=0`，
注释写明「引擎内不做连接级重试——死源一次超时已耗尽预算，重试把最坏
代价翻倍」。**同一条教训在 anysearch 里没被应用。**）

### 2.2 影响面（量化）

| 类别 | 数量 | 说明 |
|---|---|---|
| 有 HTTP 级重试的 builder | **1**（anysearch） | 独有 |
| 未声明 timeout 的引擎 | 7 | 会被施加引擎级重试（2×）|

所以 4× 叠乘是 anysearch 独有；但 2× 叠乘影响 7 个引擎
（local_search / anysearch / twitter / reddit / xiaohongshu / bilibili / weibo）。

### 2.3 为什么「逐处调小超时」不是好解法

那会**误杀慢网下正常的源**。真正的解法是给**单个引擎的总墙钟**设上界——
无论嵌套几层重试都兜得住，且对未来新增的重试层同样生效。

## 三、修复：三层叠加

### 3.1 通用层：每引擎墙钟预算（根本解）

`search.py` 新增 `_PER_ENGINE_BUDGET_S = 10.0`，在 `_exec_engine` 中：

```python
# 每次尝试的可用超时 = min(声明超时, 剩余预算)，下限 0.5s
attempt_to = min(to, max(0.5, _eng_budget - elapsed))
```

**关键语义**：
- 首试也受预算约束（否则 fast 的 6s 总预算会被 8s 首试突破）
- 后续尝试自动收缩到剩余预算 → 单引擎总耗时不越界
- **首次必须发出**（见 §4.2 的教训）

取值 10s 的理由：用户明确的体感阈值，且 ≥ `execution.default_timeout(8s)`
保证单次正常尝试不被截断。新增 `TestBudgetConstant` 守卫这个区间。

### 3.2 引擎层：anysearch 去重试

```python
# max_retries=0：不再做引擎内连接级重试
# 失败切换的职责在编排层（熔断降权 + hedged 补发备选 + 每引擎墙钟预算），
# 引擎内重复尝试只会放大延迟。
client = HttpClient(timeout=to, max_retries=0, jitter=False)
```

### 3.3 配置层：声明 timeout 关掉逃生门

`config.yaml` 给 anysearch 补 `timeout: 8` → `_engine_retries` 返回 0。

## 四、验证

### 4.1 行为验证（挂起引擎）

注入一个「睡满超时」的引擎，测三种模式的**总耗时**：

| 模式 | 修复前 | 修复后 | 超时序列 |
|---|---|---|---|
| auto | 31.3s | **10.1s** | `[8, 1.93]` ← 第二次被压缩 |
| fast | — | **6.1s** | `[6.0]` ← 首试也被 6s 预算收紧 |
| deep | 31.3s | **10.1s** | `[8, 1.93]` |

超时序列 `[8, 1.93]` 是设计意图的直接证据：**第二次尝试的可用超时
自动收缩为剩余预算**（10 − 8 = 2s 左右）。

### 4.2 一个我引入的回归（被既有测试抓住）

首版守卫写成「剩余预算 ≤0.5s 就 break」，**包括首次尝试**。
结果：预算较小（如测试 patch 的 0.5s）时**引擎根本没被调用**，
outcome 从 `timeout` 变成 `no-results`——语义从「慢」变成「没尝试」。

既有测试 `test_race_fast_budget_0906` 立即报错：

```
slow_bad_a 被标成 no-results（应为 timeout）
```

**修正**：只跳过**后续**尝试，首次必须发出。这也说明了既有测试网的价值。

### 4.3 备选源切换验证（你的第二个要点）

**产品行为是正确的**——实测慢主引擎 + 快备选：

```
耗时 2.24s | 调用=[slow_primary(timeout=8), fast_backup]
结果 2 条，全部来自 backup
engine_outcomes: [('fast_backup','ok',3), ('slow_primary','timeout',0)]
```

即：**主引擎超过 grace（2s）未完成 → 补发备选 → 采用备选结果 → 不等主引擎**。
总耗时由备选决定，慢主引擎被记录为 timeout 后弃置。

新增 `TestBackupFailover` 锁定这个契约。

## 五、顺带修掉批次三的一个潜伏 bug

排查过程中发现：**`_lang_compatible('zh', 'ja')` 返回 `True`**。

根因：批次三的 `result_lang._SCRIPT_FAMILY` 里有 `cjk: {zh, ja}`。

**为什么这是真 bug**：
- 汉字在中日文之间共享，但 zh 与 ja 是**不同语言**
- 后果①：中文结果通过日语查询的语言校验，噪声理由被误写成「语言相符」
- 后果②：相关度处于 0.2~0.5 的中文结果被判 `low` 而非 `noise`，**漏过噪声门**
- 这正是「日语查询返回中文结果」的成因之一（你早先指出的现象）

**修正**：移除 `cjk` 族。保留 `latin`/`cyrillic` 是因为结果侧检测器对
这两类**只能给到语系级**（纯西里尔文本分不出 ru/uk/bg），此时兼容判断
是必要的；而中日文检测器能给到具体语种，就不该再合并。

修正后：

```
_lang_compatible('zh','ja')       = False  ✓
_lang_compatible('cyrillic','ru') = True   ✓（语系级仍兼容）
日语查询 + 中文结果 → lang_match=False, verdict=noise, 理由准确 ✓
```

## 八、收尾：预算可配 + 6 引擎核查

### 8.1 预算提升为配置项

`execution.per_engine_budget_s`（默认 10），读取时对非法值安全回落：

| 输入 | 生效预算 |
|---|---|
| `10` | 10s |
| `"abc"` | 10s（回落） |
| `0` / `-1` | 10s（回落） |
| `None` | 10s（回落） |

**行为验证**（改配置 → 挂起引擎耗时随之变化）：
`per_engine_budget_s=3 → 3.1s`、`=6 → 6.1s`、`=10 → 10.1s`。

### 8.2 6 个引擎逐个核查

核查产出**一个必须区分的二分**（这是本轮最重要的发现）：

| 引擎 | 内部重试 | 实测延迟 | 决策 |
|---|---|---|---|
| weibo | **有**（429+URLError，3 次带退避） | 0.40s | **声明 timeout=8** |
| reddit | **有** | 中位 1.20s / 最大 3.16s | **声明 timeout=8** |
| bilibili | **有** | 0.62s（稳定） | **声明 timeout=8** |
| twitter | **有** | 不可路由（缺 tw） | 声明 timeout=8（保持一致） |
| local_search | **无** | 中位 0.00s / 最大 1.31s | **不声明** |
| xiaohongshu | **无** | 不可路由（缺 xhs） | **不声明**，但修内部 15s |

**为什么不能一刀切**：

- **有内部广谱重试的引擎**：必须声明 `timeout>=8` → 关掉外层重试，消除叠乘
  （weibo/reddit/bilibili/twitter 的内部重试与 anysearch **同构**：
  `_http_get_with_retry` 对 429 与 URLError 都重试，最多 3 次带指数退避）
- **无内部重试的引擎**：**不该**声明 → 否则关掉外层重试 = 一次失败即放弃，
  **降低成功率**。`local_search` 无重试且极快（<1.5s），不构成长耗时风险

### 8.3 发现并修掉「内层白跑」

`xiaohongshu` 内部硬编码 `subprocess.run(timeout=15)`，**长于外层预算 10s**。

实测确认了约束关系：外层 `subprocess.run(timeout=N)` 会**硬 kill** 子进程
（验证：外层 2s、内层要 10s → 实际 2.0s 返回）。所以：
- 总耗时**受控**（预算有效）
- 但内层那 15s 是**白跑**（已消耗的 CPU/网络追不回）

已改为 8s 且可用 `ARGO_XHS_TIMEOUT` 覆盖（默认短于预算，内层能主动超时
返回而非被 kill）。

### 8.4 校验闭环

新增 `test_timeout_declaration_policy.py`（10 用例），并做**双向变异测试**：

| 变异 | 预期 | 结果 |
|---|---|---|
| 移除 weibo 的 timeout | 报「叠乘」 | ✅ 失败并指明 `weibo(timeout=None)` |
| 给 local_search 声明 timeout | 报「降低成功率」 | ✅ 失败并指明 `local_search(timeout=8)` |

**测试自身的两个缺陷也已修**：
1. `local_search` 的实现在 `sub-skills/` 下，首版路径解析找不到 →
   断言**空转跳过**、给虚假安全感。已改为从 config 的 `cmd` 字段回落解析
2. 「找不到源码就跳过」改为**显式失败**，避免同类空转
