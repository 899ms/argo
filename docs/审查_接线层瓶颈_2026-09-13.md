# 审查报告：接线层是当前最大的瓶颈

- 日期：2026-09-13
- 范围：v2.8.8 之后未提交的批次九改动（38 文件 / 1892 行新增）+ 状态层修复轮
- 方法：先测量后结论；每个判据都可复现
- 结论：**瓶颈不在检索质量、不在延迟、也不在状态层（上一轮已修），
  而在「新增引擎 → 真正参与路由」这条转化链上的手工接线。**

---

## 一、重新定义问题：先把默认假设排除掉

「最大瓶颈在哪里」的默认答案是质量或速度。先测这两项：

| 观察项 | 实测 | 判据 |
|--------|------|------|
| 路由耗时 | 9.2 ms/查询（20 条中英日韩混合查询） | 不是瓶颈 |
| 融合层 | 本轮已修匿名键碰撞 + 补跨引擎共识先验 | 刚改善过 |
| 全量回归 | 1735 通过 / 0 失败 / 89 s | 不是瓶颈 |
| 上一轮结论 | 状态层数据是假的（已修：并发写 235→0 崩溃、丢失 68%→0） | 已解决 |

排除了这三项之后，线索来自一批「装好了但用不上」的引擎。

## 二、量化：供给很大，接线很少

| 指标 | 数值 | 来源 |
|------|------|------|
| 已声明引擎 | 216（config.yaml 157 + `engines/specs/*.yaml` 59） | `sync_backends.py --check` |
| 域 | 88 → 89 | 本次新增 kor_law 域 |
| 单次查询平均实际参与的引擎数 | **2.5** | auto/balanced 域 combo 截断后 |
| auto 域组合中出现过的引擎 | 121 / 204（enabled） | 静态扫描 |
| 无任何域引用的 enabled 引擎 | 47 | 静态扫描 |
| 路由层任何位置都未引用的引擎 | 5 | 结构化+字面量扫描 |
| 批次九成本 | 25 引擎 / 38 文件 / 1892 行 | `git diff --stat` |

**单个新引擎的边际成本 ≈ 76 行 × 1.5 个文件**，且这些文件里有 5 处是手工清单：
`engines.py` 导入、`engines.py._BUILDERS`、`config.yaml engines`、
`config.yaml domains.engines_combo`、`route.py` 的域保护表。
两套声明机制互不相通（字段集有差异：config 独有 `env/note/requires`，
specs 独有 `latency_ms/tier/filter_args/output_format/preserve_source/recommended`），
零重叠。

结论：**新增能力的边际成本在涨，而转化率（真正参与路由的比例）在跌。**
批次九自己的文档已经承认这个症状：「装了没通电」。

## 三、MECE 分解：四层根因，每层独立可测

```
状态生命周期：声明 → 接线 → 触发 → 验证
               ①      ②      ③      ④
```

### ① 声明面：两套机制，schema 漂移

`config.yaml engines`（157）与 `engines/specs/*.yaml`（59）并列，零重叠、字段集不同。
新增引擎要先决定走哪套，且两套能表达的能力不等价。

### ② 接线面：四道互相抵消的裁剪，最后一层被前几层静默废掉

`route_query` 里决定「这次真正跑哪几个引擎」的机制现在有四道：

| 顺序 | 机制 | 位置 |
|------|------|------|
| 1 | 能力族去重（web_general 至多 2 个）+ 互补回填 | `_get_engines_combo` |
| 2 | 意图裁剪（definition/fact→1、news→2、compare/social/research→3） | `_apply_intent_parallelism` |
| 3 | 模式预算截断（fast 2 / auto 3 / deep 不截断） | `filter_combo_by_policy` |
| 4 | 垂直域新专源加槽（批次九新增） | `_new_source_budget_extra` |

第 4 道是专为「装了没通电」加的补丁，但它在 1、2 之后运行，且额度按
**当前 combo** 的位次计算——新源一旦被第 1 或第 2 道摘掉，额度恒为 0，
补丁静默失效。**修一层被上一层吃掉**，这是本轮最贵的发现。

实测两例（修复前）：

- `sports_search`：`openf1` / `openligadb` 未声明 `family` → 落 `web_general`
  → 被族去重（max_per_family=2）摘掉 → 加槽永不生效。
  证据：`F1 积分榜 → ['thesportsdb','jolpica','anysearch']`，
  而两引擎单跑正常。
- `org_entity`：`ror` 被意图裁剪摘掉 → 加槽永不生效。
  证据：`研究机构 标识 → ['wikidata','baidu_baike','zh_wikipedia']`。

### ③ 触发面：域 pattern 覆盖缺口

- `kor_law` 引擎声明齐全（enabled / free / family=legal）、能 `--engine` 单跑，
  但**配置里根本没有对应的域**——`japan_law` 的 desc 还写着
  「与 flk_law/kor_law 构成东亚法条三源」，说明接线是漏的。
  证据：`韩国 法律 → chinese_general`。
- `org_entity` 的 combo 里有 `ror`，但全部 pattern 都在讲政府/公司实体，
  没有一条能把科研机构标识类查询送进该域。
- 语言面：中文法条查询 `刑法 判例 司法解释` → 域 `legal`，但 TF-IDF
  把 `kor_law`（`ENGINE_LANGS=["ko"]`）注到了**第一位**——中文查询优先去打了
  韩国判例库。语言可达性门（`lang_allows`）当时只对 ja/ko 查询生效。

### ④ 验证面：门禁复制生产表，且带 `or True`

`tests/test_new_source_reachability.py` 有三处失效：

1. `NEW_SOURCES` 是 `route._VERTICAL_NEW_SOURCE` 的**手工副本**——测试锁的是
   自己抄的表；
2. 「一致性校验」写成 `assert f'"{domain}"' in inspect.getsource(route)`——
   子串匹配，把真表整段删掉也能过（域名字还在注释里）；
3. `combo = [e for e in _domain_combo(domain) if e in _enabled(domain) or True]`
   —— `or True` 让 enabled 过滤彻底失效。

结果就是：这份门禁**全绿**，而上面 ①②③ 的缺陷全部在场。

## 四、本轮修复

### A. 同一 bug 类没修完（原子写）

状态层那轮把固定 tmp 名的原子写收口到 `argo_paths.atomic_write_json`，
但同类写法还有 3 处未改，且 `mcp_setup.py` 自带一份重复实现。

| 文件 | 处理 |
|------|------|
| `scripts/job.py` 快照写 | → `argo_paths.atomic_write_json` |
| `scripts/fetch_v3.py` 移动身份记忆 | → 同上 |
| `scripts/redskill/redskill_engine.py` 14.6MB 缓存 | → 同上 |
| `scripts/mcp_setup.py` 自带 `atomic_write` | → 提升通用原语 `atomic_write_text`（含 `mode`），JSON 版转发到它，删重复实现 |

固定 tmp 名的后果：并发进程互相搬走临时文件 → `os.replace` 抛
FileNotFoundError → **状态静默丢失**（这也是上一轮 `errors > used` 的来源）。

### B. 死代码 / 死参数 / 格式

- `route._new_source_budget_extra` 的 `pure_combo` 参数：只有 modal_card 会传 True，
  而该域不在 `_VERTICAL_NEW_SOURCE` 表里 → 恒无效，删除。
- `route_query` 内 `_VERTICAL_KEEP` 每次调用重建 18 元素 frozenset → 提升为模块级常量。
- `route_query` 两处逐字相同的 `_budget_extra` + `_apply_engine_policy` 调用块
  → 收敛为 `_apply_policy_with_new_source_slots` 单一入口。
- `search.local_five_dim_rerank` 的 `if len(enriched) < len(_priors)` 是恒真守卫，
  会让「下标错位」这种真缺陷静默退化为 `prior=0` → 改 `enumerate` 对齐。
- `url_canon` 的 `fold_www` / `fold_mobile` 两个开关被合进同一个正则，
  任一为真就剥两类前缀（开关名不符实）；且前缀集合里混进 `ww1|ww2`（疑似笔误）。
  → 拆成两条正则，逐个剥离，各自保留「剩余 ≥2 段」守卫。
- `engines.py._BUILDERS` 有一行挤了两个键（`"met_museum": ...,    "github": ...`）
  → 拆行。（同时用 AST 检查了 127 键无重复键、config.yaml 无重复键。）

### C. 接线层真根因修复

| 缺陷 | 修法 |
|------|------|
| `openf1`/`openligadb`/`jolpica` 被误判为 `web_general` | 三个 spec 补 `family: sports`（与其 `coverage: [sports, …]` 一致，与 `thesportsdb` 同族） |
| 加槽额度被前置裁剪吃掉 | 额度改按域**声明**位次计算；被摘掉的新专源在同一额度内补回（额度不足时不强塞，交回既有 must_keep 换位逻辑） |
| `kor_law` 无域可达 | 新增 `kor_law` 域，触发词带韩国语境限定（谚文作强信号；汉字词必须带韩国语境，直接复用 `japan_law` 踩过的教训） |
| `ror` 无触发词 | `org_entity` 补两条带**标识语境**的 pattern（标识/编号/机构号/域名/ROR），避免裸「大学/研究所」整片吸走 |
| 语言门只对 ja/ko 生效 | TF-IDF 前置注入改为对**所有**查询应用 `lang_allows`（复用既有 canonical helper，非新机制） |

### D. 门禁加固（防止同类缺陷复发）

`tests/test_new_source_reachability.py`：

- 删除 `NEW_SOURCES` 副本，改为直接读 `route._VERTICAL_NEW_SOURCE`（单一真源）；
- 删掉子串断言，换成「真源非空且与展开一致」的语义断言；
- 去掉 `or True`；
- **新增端到端探针门禁**：对每个声明了新专源的域，用典型查询真跑一遍
  `route_query`，断言该新源出现在最终引擎列表里。

这条探针门禁在加固当场就抓出了 `sports_search` 与 `org_entity` 两个真实缺陷
（旧门禁全绿）。

## 六、结构性提案（未实施，需拍板）

这一轮的修复让**现有**机制重新生效，但没有拆掉那个「四道裁剪互相抵消」的结构。
下次再加一批引擎，同类问题会以新形态回来。可考虑的收敛方向：

### 提案一：把四道裁剪收敛成一次「按声明优先级的单次预算」

现在四道裁剪各自持有截断权，后加的补丁必须知道前面各道摘了什么才可能正确。
改成：域**声明**一份带角色的优先级列表（`primary` / `specialist` / `general`），
`route` 只做一次截断，规则是「general 类先被裁，specialist 类由域作者显式声明即保留」。
这样 `_VERTICAL_KEEP`（18 个域的手写名单）、`_VERTICAL_NEW_SOURCE`（7 个域）、
`budget_extra` 三个机制一起消失，也不再需要「加槽 vs 顶位」的区分。
**代价**：要重排 89 个域的 combo 语义，回归面大，需专门一轮。

### 提案二：合并两套引擎声明机制

`config.yaml engines` 与 `engines/specs/*.yaml` 字段集已收敛到只差
`env / note / requires`（config 独有）。补齐这三个字段到 spec schema，
把 config.yaml 的 157 个引擎声明迁到 `engines/specs/`，然后删掉 config.yaml 的
`engines:` 段。收益是「一个引擎一个文件」，字段能力不再分叉。

### 提案三：扩充**既有**可达性门的取源路径（更正）

本仓**已经有**一条经过验证的可达性门：
`scripts/matrix_search_eval.py::run_offline_reachability`（离线跑，
`python3 scripts/matrix_search_eval.py --offline`）。它的取源路径比我
在审查过程中临时重建的那套更全：域 combo / `GENERAL_FREE_FALLBACK` /
选题 profiles（`topic_research_profiles`）/ 研究 boosts /
`backends/domain_profiles.json` 中 documents 非空的 TF-IDF 画像 /
`local_*` 经 local_search 展开；并区分「声明 explicit_only」与「真死源」。

**本报告初稿在此处有误，更正如下**：初稿写「静态可达性判据不成立，
自建判据产出 30 个误报，故未加门禁」。实际是我漏掉了上面那几条路径
（例如 `open_meteo` 经选题 profile 可达、`local_*` 经 local_search 展开），
不是判据不成立。既有门禁是可用的——实测：

| 版本 | 死源数 | 明细 |
|------|--------|------|
| 公开版 v2.8.6 | 8 | datacite, firecrawl, fxtwitter, sec_edgar, tinyfish, tinyfish_news, tinyfish_paper, zenodo |
| 本地（本轮后） | **0** | 全部已接线或转 explicit_only 声明 |

所以这一项的正确做法不是新造声明机制，而是：**把「域声明的新专源」这类
路径也纳入既有门的取源集**（本轮的加槽机制就是这类路径，它此前不在门禁
视野里，所以门禁报 0 死源、而下游仍可能选不中——本轮新增的端到端探针门禁
补的正是这一段）。

### 提案四：`route.py` 体积治理

`route.py` 已 1800+ 行，是最大的逻辑文件，且每批次都要手改其中的域保护表。
建议把「域 → 引擎组合策略」整体移到 `config.yaml` 或一个 `domain_policy.py`，
让 `route.py` 只保留「读策略 → 执行」的骨架。

## 七、元教训

1. **补丁叠补丁时，最新的补丁可能被更早的机制静默废掉。** 批次九的加槽机制
   写得很仔细（额度分档、上限保护、注释齐全），但它算错了输入——用了已被裁剪的
   combo。这类缺陷不会报错，只会表现为「功能没效果」。
2. **测试复制生产表 = 没有测试。** 抄一份表再断言它，锁住的是抄写那一刻的快照。
3. **`or True` 这类「临时放宽」会永久化。** 它让 enabled 过滤失效整整一轮。
4. **门禁要跑到端到端。** 策略函数层面的断言（复刻口径）看不见管线顺序，
   只有真跑 `route_query` 才能发现「前面的裁剪把源摘了」。
5. **「门禁报 0」不等于「下游能选中」。** 既有可达性门答的是「有没有任何路径
   指向这个源」，端到端探针门答的是「这条路径在真实管线里是否真的生效」。
   两者不可互相替代：本轮的加槽机制在门禁看来「可达」，实际却被前置裁剪废掉。
   另：审查时若自建判据得出与既有门禁相反的结论，先怀疑自己的取源集不完整
   （本报告初稿即犯此错，见提案三的更正）。
