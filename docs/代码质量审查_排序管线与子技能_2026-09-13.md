## 一、最大瓶颈：共识信号三处重复计分（量化）

跨引擎共识是 RRF 融合的核心产出。实测它在**三个独立位置**进入最终分：

| # | 位置 | 形式 | 代码 |
|---|---|---|---|
| ① | 五维 rerank 内部 | 加法先验，`W_PRIOR=0.12` | `search.py:825-852` 定义，`:896` 调用 |
| ② | 五维 rerank **之后** | 乘法 `×(1+0.05·min(n-1,3))` | `search.py:1927-1931` |
| ③ | evidence selection 回填 | 乘法 `×(1+0.1·min(n-1,2))` | `search.py:1949-1951` |

对一条 3 引擎共识条目（n=3）的实测累计增益：

```
base(五维原始)      = 0.5000
+ ① prior 加法      = 0.5400  (+8.0%)
+ ② 乘法 boost      = 0.5940  (+10.0%)
+ ③ selection 乘法  = 0.7128  (+20.0%)
合计相对 base       = +42.6%
对比：单源条目 n=1，三处全不触发，增益 = 0%
=> 3 引擎共识 vs 单源，最终分数差 1.43x
```

**为什么这是缺陷而非特性**：①的注释明确写「共识数按 `min(n-1,3)/3` 计（**与 `apply_consensus_boost` 的封顶口径一致**）」——作者知道②存在并刻意对齐口径，但没有意识到**对齐口径不等于避免重复计分**。三处各自都「合理」，叠加后单条信号被放大 42.6%，而设计文档里找不到任何理由支持这个量级。

### 复现证据（合成数据，确定性）

```python
A/B/C 三引擎各返回同一条 URL（3 引擎共识）
D 单引擎返回一条长摘要条目
rrf_merge 后:  x.com/a rrf=0.04918 cons=3  |  y.com/b rrf=0.016393 cons=1
五维 rerank 后: a.com/x score=0.5632 prior=0.8333 comp=0.209
                b.com/y score=0.3500 prior=0.1667 comp=0.500
=> prior 高 5 倍，仍只赢 0.21——因为 comp(摘要长度) 差 0.29
=> 再叠加 ② 的 ×1.1，a 变成 0.6195
```

### 更深一层：五维权重与维度动态范围错配

权重本身看起来均衡（通用域 rel .264 / auth .264 / fresh .176 / comp .132 / nov .044 + prior .12），但**权重乘以「该维度实际变化范围」才是实际影响力**：

| 维度 | 权重 | 实测动态范围 | 实际影响力 | 说明 |
|---|---|---|---|---|
| authority | 0.264 | 0.45（0.45→0.9） | **0.119** | 最大实际影响源 |
| prior | 0.120 | 1.0 | 0.120 | 但已被 ②③ 再放大 |
| completeness | 0.132 | 0.29（实测 0.09→0.38） | 0.038 | |
| relevance | 0.264 | ~0.13（实践中饱和） | **0.034** | 权重最大、影响力倒数 |
| novelty | 0.044 | 0.67 | 0.029 | |
| freshness | 0.176 | **~0**（大量恒为 0.5） | **~0** | 权重第二梯队，实际零影响 |

`_score_relevance` 是 token 覆盖率（`search.py:805-813`）。实测 8 个真实查询 × 4 类文本共 32 样本，值域 `[0, 1]` 但实践中聚集在少数档位；而 `freshness` 在无 `published_at` 时恒返 0.5，占 0.176 的权重却贡献零信息。

**结论**：现在真正决定排序的是 `authority`（0.119）而不是 `relevance`（0.034）——这与「搜索的第一性是相关」相矛盾。

### BUG-1 【严重·活 bug】`except TimeoutError` 在 Python 3.9 永不触发

```python

...
```

**实测复现**（本机 Python 3.9.6，最小可复现代码，非推测）：

## 五、结构性代码质量问题

### 5.1 文件膨胀失控（**presumptive blocker**）

`search.py` 从 v2.8.6 的 2580 行 → v2.8.8 的 **2833 行**，且**从未低于 1000 行的健康线**。`execute_search` 单函数 **1032 行 / CC=314**，内含 **146 个 if/for/while、29 个 try 块、9 个嵌套函数**——这是一个函数里塞进了一整个搜索引擎的编排逻辑。

审查规则要求「不允许 PR 把文件从 1k 以下推到 1k 以上」，此处更严重：**它早在 1k 以上，而每次批次都在继续往上加**。`scripts/` 下已有 **9 个文件超 1000 行**（`search.py` 2833、`engines_builders_data.py` 2728、`engines_builders_cn.py` 1900、`route.py` 1803…）。

**code-judo 机会**：`execute_search` 的 29 个 try 块几乎全是「可选依赖降级」模式（`except ImportError: pass` / `except Exception: log.debug`），这正是可以整体消除的复杂度类别——用一个显式的 `OptionalStage` 注册表替代散落的 try/except，能让 29 个分支坍缩为一次表驱动分派。这不是「把代码搬个位置」，是**删掉一类复杂度**。

### 5.2 特例分支堆积（spaghetti growth）

`local_five_dim_rerank`（`:854-998`，145 行 / CC=33）中有一串**域特例保底**：

```python

if domain == "stock_query" and _src_has(source, "tencent_quote"):relevance = max(relevance, 1.0)
if domain == "stock_query" and _src_has(source, "em_flow"):      relevance = max(relevance, 0.9)
if domain == "macro_data" and _src_has(source, "fx_rate"):       relevance = max(relevance, 0.9)
if domain == "macro_data" and _src_has(source, "worldbank"):     relevance = max(relevance, 0.85)
if domain == "financial_news" and _src_has(source, "cninfo"):    relevance = max(relevance, 0.85)
# 外加 authority 保底 6 个 source、freshness 保底 4 个 source
```

**16 个硬编码的 (域, 源) → 分值 映射埋在排序核心函数里**。每接一个新源就可能要再加一行。这是审查规则明确点名的「feature-specific logic leaking into a shared path」。

**code-judo 机会**：这些分值本质是**源自身的属性**，应该进 `config.yaml` 的引擎声明（`relevance_floor` / `authority_floor` / `answer_type`），由 `engines_base` 统一透传。这样排序函数对「源的类型」完全无知，16 个分支变成 0 个分支，且新源接入时改配置而非改排序代码。

### 5.3 幽灵引用：注释指向不存在的符号

`search.py:839` 注释写「与 `apply_consensus_boost` 的封顶口径一致」，但 `grep -n "apply_consensus_boost" scripts/search.py` 显示**该名字只出现在注释里**——`:1927-1931` 的实际实现是内联在 `execute_search` 中的循环。账本记录 A 阶段抽出了 `apply_consensus_boost(17/CC7)`，但当前代码里它是内联的，说明**抽取后被回退或从未接线**。这类「注释指向不存在的符号」会让后续维护者按错误指针找代码。

### 5.4 排序语义被下游分支改写

`search.py:1932`：`merged.sort(key=lambda r: abs(r.get("score", 0) or 0), reverse=True)`。

用 `abs()` 排序是**防御性代码掩盖不变式**：如果 score 可能为负，那是上游 bug；用 `abs()` 会让负分条目**跳到最前面**（`abs(-0.5) > abs(0.3)`），把「数据错误」变成「静默的错误排序」。类型/不变式应该在边界处变显式（assert 或 clamp），而不是在下游用绝对值粉饰。

## 八、结论

**最大瓶颈**：排序管线的**信号设计**，而非速度或数据源。共识信号被三处重复计分（实测 +42.6%），五维权重与维度实际动态范围错配（authority 0.119 vs relevance 0.034），且**没有任何分级度量能发现这个问题**（全仓零 nDCG/MRR）。

**最该先做的三件事**：
1. **P1-4 建度量基建**——否则后面所有排序改动都是盲改。这是最高杠杆且零风险。
2. **P0-1/P0-2 修两个活 bug**——`TimeoutError` 跨版本失配、seek 把工具缺失伪装成搜索结论，都是本机 100% 触发的真实故障。
3. **P0-3 让 `url_canon` 收编做完整**——6/9 发散的归一化正在让 ego-search 的融合报告形同虚设。

**最该避免的**：继续往 `execute_search`（1032 行/CC=314）里加分支。它已经是一个函数装下整个编排层，每次批次都在往上加。
