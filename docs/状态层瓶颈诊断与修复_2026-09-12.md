# argo 瓶颈诊断与状态层缺陷修复报告

- 日期：2026-09-12
- 范围：`~/.agents/skills/argo`（v2.8.8）
- 方法：第一性原理 + MECE + 量化实证；先测量再动手，每个结论都由可复现的实测支撑
- 结论：**瓶颈不在搜索质量，而在「驱动路由决策的状态层本身是损坏的」**

---

## 一、重新定义问题

原始问题是「argo 最大的瓶颈在哪里」。

第一次测量就否掉了默认假设——瓶颈不在检索质量：

```
查询=python dataclasses   engine=octen        top1 score 0.8792
查询=贵州茅台股价          engine=sina_quote   top1 score 0.9
```

相关度正常、路由正确、延迟可接受。真正的问题在别处。

**线索是一组「不可能的数据」**：真实 `quota.json` 里 16 个引擎出现
`errors > used`：

| 引擎 | used | errors |
|------|------|--------|
| github | 1 | 78 |
| anysearch | 3 | 450 |
| zhihu | 0 | 14 |
| openverse | 30 | 30 |

错误次数不可能超过调用总次数。这不是统计口径问题，而是**状态写入在丢失**。

### 关键认识：这套状态正在驱动决策

`quota.json` / `circuit_breaker.json` 不是日志，它们直接决定路由：

- `route.py:1034` 按 `is_available()` 剔除不可用引擎
- `route.py:888` 按 `is_hard_down()` 全模式排除配额耗尽引擎
- `route.py:1045` 按 `breaker.allow()` 剔除熔断引擎，决定候选滚动

所以状态损坏 = **路由基于假数据做决策**。这才是瓶颈：

> 搜索质量的上限，被「引擎可用性判断的准确性」压住了。
> 而可用性判断的数据源，正被并发写系统性破坏。

## 二、MECE 分解：五类缺陷

按「状态从产生到被消费」的生命周期做 MECE 切分，每类都独立可测：

```
状态生命周期：写入 → 并发 → 口径 → 消费 → 入口
              ①      ②      ③     ④      ⑤
```

### ① 写入不原子（固定 tmp 名）— P0

`quota.py:_save_state` 用**固定文件名**做临时文件：

```python
tmp = QUOTA_STATE_PATH.with_suffix(".json.tmp")  # 所有进程同名！
tmp.write_text(...)
tmp.replace(QUOTA_STATE_PATH)
```

A 进程 `replace` 时会把 B 进程的同名 tmp 一起搬走，B 再 `replace` 就抛
`FileNotFoundError`。

**实测（6 进程 × 60 次写入）**：

| 指标 | 修前 | 修后 |
|------|------|------|
| 崩溃次数 | **235** | **0** |
| 成功写入 | 125 | 360 |
| 状态丢失率 | **68%** | **0%** |

同类写法还有 3 处：`circuit_breaker.py:60`、`lang_pref.py:163`、
`v2ex_nodes.py:120`。

### ② 跨进程无锁（丢失更新）— P0

修掉固定 tmp 名后崩溃降为 0，但**状态仍丢失 77%**。原因更根本：

进程内 `threading.Lock` 挡不住跨进程。A 和 B 各读到旧状态、各自 +1、
后写者覆盖前写者（read-modify-write 丢失更新）。

这是「修了症状、没修根因」的典型：崩溃消失了，但数据依然丢，而且
**丢得更安静了**——这正是最危险的形态。

### ③ 统计口径分子分母不同窗口 — P1

```python
def get_error_rate(self, engine):
    total = len(state.get("calls", []))   # 分母：只留最近 1 小时
    return state.get("errors", 0) / total # 分子：永久累计，从不衰减
```

两个窗口不一致。**实测：1 次成功调用 + 历史 3 次错误 → 错误率 3.0（300%）**。

这也解释了 `errors > used`：`used` 被 1h 修剪、`errors` 不修剪。

### ④ 逐引擎落盘（写放大）— P1

每次 `record()` 都是「全量状态序列化 + rename」。一次 5 引擎搜索 = 5 次
全量写。状态文件随引擎数增长（289 引擎 ≈ 560 KiB），写放大线性叠加。

### ⑤ 入口在 Python 3.9 崩溃 — P0（用户可见）

`bin/argo:39`：

```python
def _engine_count() -> int | None:   # 3.10+ 语法
```

macOS 系统 `/usr/bin/python3` 是 **3.9.6**，执行到模块级注解求值就抛
`TypeError`。

**最讽刺的地方**：同文件里 `_pick_python()` 函数**正是为了兼容 3.9 而写的**
（注释明说「macOS 默认 3.9，而 argo 脚本用了 3.10+ 语法」）。但注解在
`_pick_python()` 有机会执行之前就崩了——**防火门建好了，却被自己的门槛挡在外面**。

`argo --help`、`argo 任意子命令` 全部失效，只有 5 个测试用例覆盖到了。

## 四、修复实现

### 核心设计：把原子写提升为单一真源

缺陷 ①③④ 的共同根因是「每个模块各自手写持久化」。修法不是逐个打补丁，
而是在 `argo_paths.py`（argo 既有的「本地状态目录单一真源」）新增两个原语：

**`atomic_write_json(path, payload)`**

- 用 `mkstemp` 取**进程内唯一**临时名（同目录，保证同文件系统 rename 语义）
- 失败路径只清理**自己的** tmp，绝不触碰别人的
- 统一 `indent`、`ensure_ascii=False`

**`file_lock(path, timeout=10)`**

- 跨进程 flock 排他锁
- 锁在**独立的 `.lock` 文件**上——数据文件靠 `os.replace` 整体替换，
  若锁与数据同 inode，替换后新进程会锁到另一个 inode 而形同无锁
- 拿不到锁（平台不支持）则 **fail-open**，绝不因观测层阻断搜索主路径

### 各模块改造

| 文件 | 改动 |
|------|------|
| `argo_paths.py` | 新增 `atomic_write_json` / `file_lock` / `isolate_state_dir` |
| `quota.py` | 写盘走单一真源；新增 `_mutate_locked`（锁内重读-改-写）；新增 `record_many` 批量落盘；`_prune_locked` 让 calls/errors 同窗口修剪；`get_error_rate` 改同窗口口径 |
| `circuit_breaker.py` | `_save` 接单一真源 |
| `lang_pref.py` / `v2ex_nodes.py` | 同上 |
| `search.py` | 新增 `_QuotaBatch` 收集器，一次搜索的 N 个引擎合并为一次落盘 |
| `bin/argo` | 补 `from __future__ import annotations` + 去掉 `int \| None` |
| `ab_eval_p0p1.py` | 在 import 状态模块**之前**调用 `isolate_state_dir()` |

### 关于 `get_error_rate` 的修剪策略

`errors` 没有逐条时刻，无法精确对齐窗口。采用保守上界：

```python
st["errors"] = min(st.get("errors", 0), len(kept))
```

保证 **errors 恒 ≤ 窗口 calls**，且窗口清空则归零（无观测 = 0 错误率，
而不是拿历史错误去除）。宁可低估错误率，不虚高——虚高会误杀健康引擎。

## 七、这轮修复的元教训

1. **瓶颈常在被忽略的数据层，不在功能层。** 用户问「最大瓶颈」，默认
   会往检索质量/速度上找；实际答案是「状态层数据是假的」。

2. **`errors > used` 这种「不可能数据」是最强的 bug 信号。** 它不可能是
   正常业务逻辑的产物，一旦出现必有写入丢失或口径错位。

3. **修了症状不等于修了根因。** 崩溃 235→0 看起来成功了，但状态仍丢
   77%。第二个根因（跨进程丢失更新）更隐蔽，因为**它不报错**。

4. **兜底逻辑必须放在它能生效的位置。** `_pick_python()` 的设计是对的，
   但放在模块级注解之后，等于没用。同理，`conftest.py` 的隔离是对的，
   但脚本 import 顺序错了就绕过它。

5. **测试要有牙齿。** 并发测试写成「同进程多线程」就永远抓不到跨进程
   bug；必须用真实子进程，且必须用变异测试证明它会失败。

## 八、一次被排除的误判（留档）

验证阶段出现过「端到端搜索返回 count=0」的现象，排查后确认**与本次改动无关**，
但排查过程本身值得留档：

- 现象：`python asyncio tutorial` 等查询返回 0 条，octen 引擎仅耗时 **5ms**
- 关键线索：5ms 不可能完成一次网络往返 → 引擎根本没打网
- 定位：`engines_builders_data.py:965` 在 `OCTEN_API_KEY` 缺失时直接
  `return []`，并只打一条 stderr warning
- 复现：手动 `source ~/.config/argo/env` 加载密钥后，同一查询返回 5 条高质量结果
  （`asyncio — Asynchronous I/O — Python 3.14.7 documentation` 等）

**根因是 shell 环境缺密钥**，而密钥真源文件 `~/.config/argo/env` 存在——
这正是 `scripts/mcp_launch.sh` 被写出来的场景（各客户端启动上下文不同）。

附带核实了空结果缓存策略：空结果以 **45 秒短 TTL** 缓存，不会长期污染；
我早前读到的 0 条是密钥缺失时刻留下的 45s 内陈旧条目。

> 教训：把「环境态缺失」误判为「代码缺陷」是这轮最容易踩的坑。
> 判定顺序应为：先排除环境（密钥/网络/权限），再看代码。
