### 2.2 关键发现：ROI 错配

**实测路由遥测（782 条真实查询）的语言分布**：

| 语言 | 占比 |
|---|---|
| 中文 | **59.6%** |
| 英文 | **25.7%** |
| 日文 | 7.0% |
| 韩文 | 4.6% |
| 其他（阿拉伯等） | **0.5%** |

**这意味着**：中英合计 **85.3%**，而 v2.6.0 与我这轮投入的「多语言长尾」
（阿拉伯/泰/越南/波兰语等）在真实使用中只占 **0.5%**。

**这不是说多语言做错了**，而是说：
- 历史多语言改进的**收益上限很低**（0.5% 的流量）
- 真正的瓶颈在**中英的检索质量**（85% 的流量）
- 且日/韩（11.6%）值得投入——它们是「次高频」，不是长尾

**建议的方向调整**：把多语言投入从「覆盖更多语种」转向
「**中英质量 + 日韩可用性**」；长尾语种维持现状（诚实降级 + 标注）即可。

## 三、搜索效率：实测差距

### 3.1 端到端耗时（同语义查询）

| 查询 | 语言 | 耗时 |
|---|---|---|
| 人工智能 | 中文 | **1.10s** |
| artificial intelligence | 英文 | 4.29s |
| 人工知能 | 日文 | **8.40s** |

**日文比中文慢 7.6 倍**。这个差距不是「多语言天然慢」，而是可优化的。

### 3.2 已定位的效率问题

1. **anysearch 单次失败耗时 31 秒**（实测）
   `max_retries=1` × 15s 超时 = 最坏 30s+。对一个已坏的上游，
   首次调用要等 31 秒才失败——用户体感极差。
   熔断器打开后（50s 冷却）才跳过，但这第一次的代价已付出。

2. **多语言查询的引擎扇出更大**
   中日英走不同域，日文域的主引擎可能超时后才有兜底。

### 3.3 建议

| 项 | 现状 | 建议 |
|---|---|---|
| 坏源首调惩罚 | 31s | 降低 `max_retries` 或用更短超时做健康探测 |
| 慢源识别 | 靠熔断（事后） | 用遥测的 latency 分布做事前降权 |
| 早停阈值 | 已有 | 结合语言能力画像（上轮产出）优化 |

## 四、高配额源审计（用户第 3 问）

### 4.1 设计意图 vs 实际使用

| 源 | 设计配额 | 实际 used | 利用率* |
|---|---|---|---|
| zhihu | 5000/天 | 1 | ~0.02% |
| zhihu_global | 5000/天 | 1 | ~0.02% |
| anysearch | 2000/天 | 7 | ~0.35% |

\* 测量口径限制：`used` 按周期重置，`calls` 只保留最近 1 小时，
故这是**量级判断**而非精确利用率。但即使按最宽松口径，
这些「用量充沛」的源也远未被用满。

### 4.2 累计错误数（更硬的证据）

| 源 | 累计 errors |
|---|---|
| **anysearch** | **448** |
| zhihu | 14 |
| zhihu_global | 9 |

### 4.3 anysearch 的真 bug（本轮修复）

**实测上游响应**：

```json
HTTP 200
{"jsonrpc":"2.0","id":1,
 "result":{"content":[{"type":"text","text":"Service temporarily unavailable."}],
           "isError":true}}
```

**旧实现的问题**：只做两件事——① 找配额关键词（quota/429/rate limit…）
② 按 `### N.` 解析结果块。「Service temporarily unavailable.」**不含配额词、
也没有结果块** → **静默返回 `[]`**。

**后果**：
- 用户看到「没有结果」，而非「上游不可用」
- 熔断器：空结果走 `empty` 分支（**刻意不驱动 open**）→ 持续空转调用坏源
- `quota.json` 累计 448 次错误，但没有任何地方能说出「为什么」

**讽刺之处**：argo **自己**在服务端输出 `isError`（`mcp_handlers.py`），
却在**消费**上游 MCP 时完全忽略它。全仓 `grep isError` 只有服务端写法、**零消费者**。

**修复**：新增 `engines_base.mcp_error_of()`，覆盖三类错误：
1. 工具级 `result.isError == true`（MCP 规范）
2. 协议级 `{"error": {...}}`（JSON-RPC）
3. 非 JSON 对象

anysearch 接入后行为对照：

| 响应 | 修复前 | 修复后 |
|---|---|---|
| `isError: true` | 静默 `[]` | `[{"error": "mcp: Service temporarily unavailable."}]` |
| 配额文本 | `[]` | `[]`（**维持原契约**，见下） |
| 正常结果 | 解析 | 解析（不变） |

**一个重要的设计区分**（我一度改错又改回）：
`isError` 与「配额耗尽」必须**相反处理**——
- `isError` 是上游**明确宣示失败** → 报错，让熔断器介入
- 配额耗尽是**临时**状态、上游健康 → 返回 `[]` 让路由优雅 fallback；
  若报错会驱动熔断 open、把「只是暂时没额度」的引擎**禁用**，反而有害

这个区分由既有测试 `test_quota_only_response_returns_empty` 锁定。
我最初把两者都改成报错，导致该测试失败——**测试纠正了我**。

### 4.4 知乎：正常

直接实测：`zhihu` 5 条、`zhihu_global` 5 条、**无错误**。
问题不在知乎本身，而在**路由选中率**（见 §2.2 的引擎分布：
zhihu 未进 Top14 被选引擎）。

## 五、可观测性：现状与设计（用户第 4 问）

### 5.1 好消息：基础设施已存在

`scripts/telemetry.py`（v2.7.2 引入）设计良好：

- append-only JSONL，失败静默（绝不拖累主路径）
- `ARGO_TELEMETRY=0` 可完全关闭
- `ARGO_TELEMETRY_DIR` 可注入（测试隔离）

**现有三个流**（实测数据量）：

| 流 | 条数 | 记录内容 |
|---|---|---|
| route | 782 | 域/引擎/置信度/语言/意图/mode |
| merge | 155 | 双源合并统计 |
| recovery | 993 | 降级/重试 |

### 5.2 缺口：缺「引擎结果」流

**现有的三个流都无法回答「anysearch 为什么失败 448 次」**：

- `route` 记录**决策**（选了谁），不记录**结果**（谁失败了、为什么）
- `merge`/`recovery` 是特定路径的专用流
- `quota.json` 只计数（`errors: 448`），**不含原因**

**这正是本轮 bug 能潜伏的原因**：引擎静默失败时，
没有任何一个地方留下「上游返回了什么」。

### 5.3 设计：`engine` 流（隐私优先）

**核心约束**（依据项目隐私规则）：

1. **绝不记录 query 原文**——`merge` 流已建立「截断」先例；
   外部提交场景必须更严格
2. **不拖累体验**——沿用 telemetry 的 fail-silent + append-only
3. **可诊断**——必须能回答「哪个引擎、什么错、什么时候」

**建议字段**：

```jsonc
{
  "ts": "...", 
  "stream": "engine",
  "engine": "anysearch",
  "status": "error",               // ok / empty / error / timeout / skipped
  "error_kind": "upstream",        // 复用批次一的 engine_failure 四分类
  "error_sig": "mcp:Service temporarily unavailable",  // 归一化签名（非原文全量）
  "latency_ms": 31303,
  "count": 0,
  "lang": "ja",                    // 查询语言（非查询文本）
  "query_fingerprint": {           // 不可逆的形态摘要
    "len": 12,                     // 长度
    "script": "cjk",               // 书写系统
    "tokens": 3                    // 词元数
  },
  "version": "2.8.6"
}
```

**隐私论证**：
- `query_fingerprint` 只存**形态**（长度/书写系统/词元数），
  不可反推原文，但足以聚类（「哪类查询在哪个引擎上失败」）
- `error_sig` 存**归一化签名**（如 `upstream:service-unavailable`），
  不含用户数据
- **不含** IP、hostname、路径、用户名

### 5.4 外部提交路径（可行的部分）

这是用户提出的关键需求：「通过外部提交的方式来优化」。

**建议分三档**（按隐私敏感度递增）：

| 档 | 内容 | 隐私风险 | 可行性 |
|---|---|---|---|
| **A. 本地聚合报告** | `argo health --report` 输出引擎健康摘要 | 无（不出本机） | **立即可做** |
| **B. 手工导出** | `argo health --export` 生成脱敏 JSON，用户自行决定提交 | 低 | 立即可做 |
| **C. 自动上报** | 默认关闭，显式 opt-in | 中 | 需谨慎设计 |

**建议先做 A + B**：
- A 直接解决「普通用户看有没有错误」
- B 提供「外部提交优化技能」的通道，但**由用户主动**
- C 涉及默认行为改变，且有隐私与合规负担，建议暂不做

### 5.5 与「新搜索源适配」的关系

用户提到「哪怕技能没有适配新的搜索源或 API，也可以通过这种途径优化」。

**这个思路是对的**，而且遥测能覆盖两类情况：

1. **已知源的新故障模式**——如 anysearch 的 `isError`
   （本轮已证明：没有遥测，这类问题会潜伏数百次调用）
2. **未适配源的发现**——如果用户查询在某域持续低质/空结果，
   说明该域缺数据源；遥测能暴露「域 × 语言 × 空结果率」的分布

**这正是 §2.2 那张语言分布表的产出方式**——用遥测数据做决策，
而不是凭感觉加引擎。

## 八、给你的四条建议（按优先级）

1. **调整多语言投入方向**：真实流量 85% 是中英、长尾仅 0.5%。
   把精力从「覆盖更多语种」转向「**中英质量 + 日韩可用性**」。
   长尾维持「诚实降级 + 标注」即可。

2. **先修效率最痛点**：日文 8.4s vs 中文 1.1s（7.6×）；
   坏源首调 31s。这两个是体感最强的。

3. **补 `engine` 遥测流**（§5.3 设计）：这是本轮 bug 能潜伏 448 次的根因。
   字段设计已给出，隐私约束已论证。

4. **做 `argo health --report`（本地）+ `--export`（手工导出）**：
   直接满足「普通用户记录日志看错误」+「外部提交优化」两个需求，
   且**不引入自动上报的隐私负担**。
